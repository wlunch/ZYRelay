# ZYRelay DocIntelligence 技术报告：模型与资源插件

**项目版本：** 1.0.0
**报告日期：** 2026-08-10
**适用范围：** PDF、DOCX 文档解析与可追溯语义提取

## 1. 系统定位

ZYRelay DocIntelligence 面向合同、制度、代码规范等非结构化文档，将原始 PDF 或 DOCX 转换为统一的 UOM JSON Package。核心结果包括文档元数据、页面或逻辑块、规则标签命中、语义索引、业务对象候选，以及每项结果对应的原文证据。

系统采取“规则优先、模型辅助”的实现方式。标签词典、正则、别名和业务对象规则仍是正式输出的主要依据；本地模型只补充文档类型、语言、版面、表格、实体、代码段或 OCR 信息。模型不可用时，系统不会伪造识别结果，而是记录原因并切换到轻量启发式方案或 NoOp 插件。因此，模型故障不会破坏现有的文档解析、标签匹配、semantic_index 和 UOM Package 主流程。

当前主链路保持为：

```text
GroundChoose → ResourcePlan → Parser → OCR Gate → Rule Extraction
→ Provenance → semantic_index → UOM Package
```

模型插件通过 `ResourcePlan` 被计划和调用，不改变该链路的权威性。每次调用都会产生 `ModelExecution`，记录插件名称、模型版本、执行时间、健康状态、是否回退和告警信息；输出中的 provenance 可用于回溯结果来自哪一个 block、哪一页和哪一次资源执行。

## 2. 当前模型与插件

| 能力 | 主插件 / 模型 | 使用条件 | 产出或作用 | 回退方式 |
| --- | --- | --- | --- | --- |
| OCR | PaddleOCR 3.7.0，PP-OCRv6-medium | 扫描型 PDF 且请求启用 OCR | OCR 行文本、位置框、置信度、页码 | `noop-ocr`，明确标记未识别 |
| 文档分类 | `all-MiniLM-L6-v2` | 文档文本可用且模型本地就绪 | contract、invoice、code_specification、general_document 等辅助类别 | 关键词分类 |
| 语言识别 | fastText `lid.176.ftz` | 对可用文本块进行语言判定 | block 的 language 元数据 | 字符集启发式识别 |
| 版面分析 | DocLayout-YOLO DocStructBench | 有可分析的 PDF 页面图像且模型就绪 | layout_type 等辅助版面信息 | parser 的 block_type |
| 表格识别 | Microsoft Table Transformer v1.1-all | 发现表格区域且模型就绪 | table_id、表格结构辅助信息 | DOCX / parser 原生表格块 |
| 命名实体识别 | GLiNER small v2.1 | 规则标签未充分覆盖实体时 | 可定位的人员、组织、地点实体建议 | 正则和启发式实体识别 |
| 代码块检测 | Tree-sitter 0.26 | 文本可能为代码、配置或 Markdown 代码块 | `is_code`、`code_language` | 模式检测 |
| 拼写建议 | SymSpellPy 6.10 | OCR 生成的文本 | 纠错建议，不覆盖原始文本 | NoOp，不输出建议 |

其中，PDF 文本和 DOCX 的基础提取不依赖上述模型：PDF 使用 PyMuPDF，DOCX 使用 python-docx。这样，普通文本型文档即使未安装任何可选模型，也可以完成分块、规则标签化、语义索引和可追溯输出。

## 3. OCR 模型的实际状态

PaddleOCR 是当前已完成离线预置和验证的模型。它部署在独立的 `.venv-paddleocr` 环境中，运行环境为 macOS ARM64，采用 CPU 推理。

- PaddleOCR：3.7.0
- PaddlePaddle：3.3.1
- 识别模型：PP-OCRv6-medium
- 已预置组件：文档方向分类、文本行方向分类、文本检测、文本识别
- 模型缓存：`data/model_cache/paddleocr/`
- 校验状态：`verified=true`，本地缓存包含 12 项文件校验记录
- 正常运行时：`allow_download=false`，不允许在文档处理请求中联网下载模型

OCR Gate 会先判断 PDF 页面是否缺少可提取文本。只有扫描页才渲染为 PNG 并送入 PaddleOCR；DOCX、原生文本 PDF 以及已有可用文本的混合 PDF 页面均不会触发 OCR。识别得到的每一行保留 `bbox`、多边形位置、置信度、模型执行 ID 和页码。原始文本块不会因 OCR 或拼写建议而被直接改写。

## 4. 其他模型的配置与当前运行状态

`config/models.yaml` 已配置 MiniLM、fastText、DocLayout-YOLO、Table Transformer、GLiNER、Tree-sitter 和 SymSpellPy 的模型标识、版本、缓存目录、启用状态和必需文件。所有缓存路径均位于 `data/model_cache/` 下，不在 Python 代码中硬编码。

在当前默认 `.venv` 的一次状态检查中，MiniLM 与 fastText 的模型文件已在缓存目录中，但其推理依赖包尚未安装；DocLayout-YOLO、Table Transformer、GLiNER、Tree-sitter 和 SymSpellPy 的依赖或完整权重尚未在该默认环境就绪。因此，它们目前会被资源计划标记为不可用或跳过，并使用配置中的 fallback。PaddleOCR 则在专用虚拟环境中已通过离线验证。

这一区分很重要：配置中 `enabled=true` 表示该能力允许被资源计划选择，不等于当前机器一定具备完整权重和 Python 依赖。实际是否调用由插件 `available()` 与 `health()` 检查共同决定，检查结果会保存进处理记录。

可使用下列命令检查和预置模型：

```bash
.venv/bin/python -m zyrelay.models status
.venv/bin/python -m zyrelay.models install all
.venv/bin/python -m zyrelay.models verify all
```

PaddleOCR 建议使用专用环境：

```bash
.venv-paddleocr/bin/python -m zyrelay.models verify paddleocr
```

管理员预置命令可以下载缺失依赖和权重；普通 Relay API 请求不会执行安装或下载操作。

## 5. 模型在处理流程中的边界

1. **规则结果优先。** 合同编号、金额、日期、主体等业务字段主要由 YAML 标签定义、正则和别名匹配产生。模型不能覆盖高置信度规则结果。
2. **所有补充结果需要证据。** NER、代码检测、OCR 等输出必须关联 block 或页码；没有可定位原文的内容不应成为正式语义对象。
3. **OCR 仅用于缺文本页面。** 系统不对所有 PDF 强制 OCR，从而避免重复处理和原文偏移失真。
4. **拼写校正不改写原文。** SymSpell 只给出建议，原始文本及其 offset 保持不变，以保证标签命中可回溯。
5. **模型失败可降级。** 发生依赖缺失、权重不完整、平台不兼容或推理异常时，系统写入 warning、fallback 标志和执行状态；核心规则流程继续运行。

## 6. 数据输出与可追溯性

模型输出会补充到 `DocumentBlock` 的以下字段：`layout_type`、`language`、`is_code`、`code_language`、`table_id`、`entities`。标签和语义索引仍以 `label_code` 为主键，每个命中保存原文、页码、block_id、起止 offset、置信度、匹配方式和 evidence。

最终 UOM Package 的 `processing` 部分记录 classifier、language、layout、table、ner、spell、OCR 等处理信息；`ResourcePlan` 与 provenance 记录计划资源和实际执行资源。用户可从 semantic_index 的某项结果回到具体文档页和文本块，进一步查看涉及的模型执行记录，而不是只获得无法解释的关键词。

## 7. 当前验证与限制

项目的离线测试已覆盖基础解析、标签匹配、索引、业务对象、模型路由与基准场景；最近一次完整测试为 **75 项通过**。PaddleOCR 专用环境已完成本地缓存验证。基准数据也验证了 block 顺序、原文证据和 provenance 的一致性。

当前限制如下：

- 除 PaddleOCR 外，部分可选模型在默认虚拟环境中尚未安装完整推理依赖或权重，因此目前以 fallback 行为为主。
- DocLayout-YOLO 和 Table Transformer 的复杂版面、跨页表格能力尚未作为生产精度承诺；基础 parser 输出仍是可靠基线。
- GLiNER 仅生成有原文位置的实体建议，不替代业务标签规则或人工审核。
- OCR 对手写文本、复杂多栏、低清扫描件的效果仍需以实际业务样本持续验证。
- 系统不包含向量数据库、知识图谱自动写入或复杂大模型推理；这些能力不属于当前可解释 MVP 的核心范围。

## 8. 结论

ZYRelay 已将轻量本地模型封装为可配置资源插件，并保留了以规则、GroundChoose、provenance、semantic_index 和 UOM Package 为中心的稳定处理流程。当前最完整验证的是 PaddleOCR 离线识别；其他模型已完成接口、配置、缓存规范和回退机制，可按部署环境逐步预置并启用。该方式优先保证文档信息可解释、可定位、可复核，再逐步提升复杂文档场景的辅助识别能力。
